# Reed Solomon

Reed-Solomon erasure coding over GF(2^8) for the Sia SDK.

A Rust translation of the synchronous, in-memory portion of Klaus Post's
[reedsolomon](https://github.com/klauspost/reedsolomon) Go library, focused on
the configuration Sia uses:

- 8-bit Galois field with generator polynomial `0x11D`
- Vandermonde encoding matrix (`V · T⁻¹`) — wire-compatible with existing Sia
  network slab data and with klauspost's default `New()`
- Optional Cauchy construction via `ReedSolomon::new_cauchy(...)`
- Pure-Rust, builds on `wasm32-unknown-unknown`, no platform-specific intrinsics

## Quick start

```rust
use sia_reed_solomon::ReedSolomon;

// 10 data shards + 20 parity = 30 total. Sia's default.
let rs = ReedSolomon::new(10, 20)?;

// Caller owns the buffers; encode overwrites the parity slots.
let mut shards: Vec<Vec<u8>> = /* 10 random shards + 20 zero-filled */;
rs.encode(&mut shards)?;
assert!(rs.verify(&shards)?);

// Drop arbitrary shards (up to 20) and reconstruct.
let mut opt: Vec<Option<Vec<u8>>> = shards.iter().cloned().map(Some).collect();
opt[0] = None;
opt[15] = None;
rs.reconstruct(&mut opt)?;
```

## Features

| Feature    | Default | Effect                                                    |
|------------|---------|-----------------------------------------------------------|
| `parallel` | yes     | Block-major / row-major rayon parallelism                 |

Disable `parallel` for WASM or other single-threaded targets:
`sia_reed_solomon = { version = "...", default-features = false }`.

## Compatibility

Bit-for-bit wire compatibility with:

- **klauspost/reedsolomon** (Go) at its default `reedsolomon.New(k, m)`
- **reed-solomon-erasure** (Rust) at its default `ReedSolomon::new(k, m)`

Verified by:

- A golden test ported verbatim from klauspost's `TestOneEncode`
  (`klauspost_one_encode_golden`)
- A 7.6 KiB golden binary generated by klauspost at Sia's exact 10-of-30 / 256 B
  config, embedded into the test binary and asserted on every `cargo test`
  (`klauspost_10of30_golden_*`)
- Round-trip tests dropping every individual shard, every contiguous max-drop
  window, and the all-data-lost-rebuild-from-parity edge case

## Benchmarks

Sia 10-of-30 (10 data + 20 parity) on 4 MiB shards, Apple M-series laptop,
`cargo bench`:

| Operation                  | `reed_solomon` (this) | `reed_solomon_erasure` | `fec_rs`   |
|----------------------------|-----------------------|------------------------|------------|
| `encode`                   | **6.0 GiB/s**         | 540 MiB/s              | 5.1 GiB/s  |
| `verify`                   | **5.5 GiB/s**         | 537 MiB/s              | 555 MiB/s  |
| `reconstruct -1 data lost` | **3.0 GiB/s**         | 355 MiB/s              | 366 MiB/s  |
| `reconstruct -10 data lost`| **3.8 GiB/s**         | 357 MiB/s              | 368 MiB/s  |

The ~11× edge over `reed_solomon_erasure` (the encoder `sia_storage` currently
uses) comes from two layered wins:

1. **Cache-blocked inner loop.** `(block, output_row, input_shard, byte)` loop
   order: each block of every input shard is read once and consumed by every
   parity row while still in L2, dropping input-side DRAM traffic from
   ~1.2 GiB to ~40 MiB per encode at this config.
2. **Rayon parallelism.** Adaptive: block-major when there are enough blocks
   to feed every core, row-major fallback for small shards.

For reference, klauspost on the same hardware would land roughly 3–5× ahead of
this crate, the gap being its hand-written AVX2/GFNI/NEON assembly (we
intentionally stay on the portable scalar path so the crate builds on
`wasm32-unknown-unknown` without arch gates).

## Why GF(2^8)?

For Sia's shard counts (≤256 total), GF(2^8) is the right field:

GF(2^16) crates (`reed-solomon-simd`, `reed-solomon-16`, `reed-solomon-novelpoly`)
use an O(n log n) FFT-based algorithm that wins above ~100 shards but adds
constant-factor overhead below that. They also produce different parity bytes
and break wire compatibility with the existing Sia network.
